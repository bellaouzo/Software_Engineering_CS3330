# File size and splitting rules

Summary table in `AGENTS.md` > File size limits. This is the full version.

Small files are easier to review, cause fewer merge conflicts between
teammates, and are easier for AI tools to read whole. Each file type has two
numbers:

- **Review at:** past this, check whether the file has started doing two jobs.
  If it has, split it. If not, say so in the PR description.
- **Must split at:** don't add more lines to a file past this. Split it first.

Count lines with `wc -l <file>` (blank lines and comments count).

## Limits

| File type | Review at | Must split at | Split into |
| --- | --- | --- | --- |
| Route module (`routes/*.py`) | 200 | 300 | One blueprint per resource |
| Other Python module (`supabase_client.py`, `auth_helpers.py`, new helpers) | 200 | 300 | One module per responsibility |
| Standalone script (`dev.py`) | 300 | 400 | A helper package the script imports |
| Any Python function | 30 | 50 | Private `_helper` functions |
| Jinja template (`templates/*.html`) | 80 | 150 | Partials in `templates/partials/` |
| CSS (`static/css/*.css`) | 400 | 600 | One file per stylesheet section |
| JavaScript (`static/js/*.js`) | 150 | 250 | One file per feature |
| `AGENTS.md` | 200 | 250 | Move detail into `docs/guides/` |
| Guide (`docs/guides/*.md`) | 250 | 350 | One topic per guide |

**Exempt:** migrations (`supabase/migrations/`), `supabase/seed.sql`,
`supabase/config.toml`, `requirements.txt`, `.env.example`, and anything
generated by a tool.

## Files that are already over

The limits apply to every file, including ones written before these rules. A
file is not grandfathered in:

- **Past "must split":** the next branch that changes the file splits it first,
  in its own commit, before the feature work. A one-line bug fix may skip this,
  but say so in the PR.
- **Past "review at":** the next branch that changes the file checks it and
  either splits it or explains in the PR why it's still one job.

Nobody needs to split every oversized file at once. Splitting happens when the
file is next touched.

## Folders and subfolders

When a split leaves several related files, group them in a folder, and nest
subfolders (and sub-subfolders) as deep as it takes to keep things organized.
The same idea works for code and docs:

- **A folder is for a group.** Create one once two or more files belong
  together. Don't make a folder for a single file.
- **Each folder has an entry point** that says what is inside: `__init__.py`
  for a Python package, `README.md` for a docs folder. A partials or CSS folder
  needs no entry file; its name is enough.
- **Name folders like files of their type:** `snake_case` for Python and
  templates, `kebab-case` for CSS, JS, and docs.
- **Prefer shallow.** Add a level when a folder holds more than about 7–8 files
  or mixes clearly separate topics, not before.
- **Moving files is a split too.** It gets its own no-behavior-change commit,
  and every import, `{% include %}`, `<link>`, `<script>`, and doc link that
  pointed at the old path must be updated.

Examples:

```
routes/
  tickets/                # package once tickets has several route files
    __init__.py            # creates tickets_bp, imports the route modules
    views.py
    comments.py
templates/partials/
  tickets/
    _ticket_row.html
    _comment.html
static/css/
  base.css
  components/
    buttons.css
    forms.css
docs/guides/
  database/               # guide that outgrew one file
    README.md              # overview of the topic, links to each subpage
    rls-policies.md
    migrations.md
```

## How to split each type

### Route modules

Split by resource, not by HTTP method. Keep GET and POST in one function (see
`conventions.md`). For example, comment routes move from `routes/tickets.py`
to a new `routes/comments.py` with its own `comments_bp`, registered in
`routes/__init__.py`. Constants and helpers that more than one blueprint uses
(e.g. `TICKET_STATUSES`, `_get_role()`) move to a plain module such as
`routes/ticket_helpers.py`. That module holds no routes.

`url_for` endpoint names change when a route moves to a new blueprint
(`tickets.<name>` becomes `comments.<name>`). Search the templates
and routes for the old name and update every match.

### Other Python modules and scripts

Split by responsibility. Each new module should be describable in one short
sentence. For `dev.py`, move groups of helpers (Docker checks, Supabase CLI
calls, venv setup) into a `devtools/` package and keep `dev.py` as the entry
point, so `python dev.py` keeps working.

### Functions

Pull self-contained steps (building a query, validating a form, turning a
Supabase error into a flash message) into private helpers with a leading
underscore, named verb-first (`_load_ticket_comments`).

### Templates

Move a self-contained block (a form, a list row, a comment) into
`templates/partials/_<name>.html` and pull it in with `{% include %}`. Partials
that need inputs use `{% with %}` or a macro.

Regardless of size, any markup that appears in **two or more** templates
becomes a partial. Copies drift apart.

### CSS

Split along the existing section headings in `app.css`, for example
`base.css` (tokens, reset), `layout.css`, `forms.css`, `tickets.css`. Link
each file from `base.html` in the original order, with the tokens (`:root`)
first, since later rules depend on them. Don't change any selectors while
splitting.

### JavaScript

Give each behavior its own `kebab-case.js` file (e.g. `submit-guard.js`,
`match-fields.js`). Load scripts used on every page from `base.html`. Load
page-only scripts from that page's `{% block scripts %}` (add the block to
`base.html` if it doesn't exist yet).

### Markdown

The docs form a tree: `AGENTS.md` is the overview, each guide covers one topic,
and a guide that grows past its limit becomes a folder with sub-guides.

- `AGENTS.md` stays an overview: one short paragraph or table per topic, plus a
  link to the guide. Detail goes in `docs/guides/<topic>.md`.
- A guide that covers two topics becomes two guides.
- A guide that is one topic but too long becomes `docs/guides/<topic>/`, with
  `README.md` as the overview and one file per subtopic. Subtopics can nest
  again the same way (`docs/guides/<topic>/<subtopic>/README.md`) when needed.
- Every level summarizes and links down. Each sub-guide starts with a line
  linking back up to its parent, so readers (and AI tools) can move in both
  directions and read only the depth they need.
- Update the links in `AGENTS.md` and the list in `docs/README.md`.

## Process

1. **Split in its own commit**, with no behavior change, e.g.
   `refactor: split comment routes into routes/comments.py`. Reviewers can
   check that nothing changed without the feature diff mixed in. A big split
   (several files) can go in its own PR.
2. **Split before adding the feature** when a file is past "must split",
   including files that were already over before these rules. Don't push it
   further over first and promise to split later.
3. **Don't split a file that is under "review at"** just to make it smaller.
   The one exception is the "used in two or more templates" partial rule.
4. **Update the docs** in the same branch: the folder structure in `AGENTS.md`,
   and any guide that names the old file.
5. **Re-run the app** (`python dev.py`) and click through the affected pages.
   A missed `url_for` rename or CSS link only shows up at runtime.

## AI agents

Before editing a file, check its line count. If your change would push it past
"must split", tell the user and propose the split (what moves where) before
writing the feature. If a file is already past "review at", mention it in your
summary even if you don't split it.
